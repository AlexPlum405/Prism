# Prism 当前 UX 优化点选择清单

> 用法：先勾选你认为要优化的问题，再勾选对应方案。未勾选的点，后续默认不做。
> 范围：基于当前 Prism 代码实现、`CONTEXT.md` 产品边界，以及 `docs/archive/dirty-data-2026-05-30/ux-audit-assets/` 下的当前运行截图。
> 原则：不换视觉方向，不回到旧 OpenAI 原型，不把 Prism 做成知识库工作台；仍然保持妙言式、本地优先、单文档 Markdown 写作器。

## 选择标签

- 【建议优先】：会明显影响日常写作或后续功能组织。
- 【体验增强】：不是阻塞问题，但做了会更顺手。
- 【低成本】：通常是局部 UI 或文案/入口调整。
- 【中成本】：需要改组件状态、交互或命令组织。
- 【高成本】：需要较完整的设计、状态模型或验证。
- 【风险修复】：不一定是普通用户立刻看到的问题，但会影响稳定性、可维护性或验证效率。
- 【暂缓观察】：现在能用，建议等真实使用反馈再决定。

## 快速判断

当前 Prism 的大方向是成立的：界面克制、内容区域舒服、左侧文件树 + 中间写作区 + 顶部菜单 + 右上视图切换的结构清楚，整体已经像一个可用的 macOS Markdown 写作器。

主要问题不是“要不要重设计”，而是下面几类：

- 入口有点分散：顶部菜单、右上图标、状态栏、命令面板、斜杠菜单、右键菜单各管一部分，用户容易不知道某个功能应该去哪找。
- 命令面板还不是真正的命令中心：现在更像“快速打开 / 全文搜索”，很多菜单能力没有接进去。
- 分栏写表格、数据、长列表时不够舒服：源码区半宽以后很容易折行，Markdown 表格尤其明显。
- 一些功能已经有了底层能力，但外层 UX 还不完整：搜索选项、文档属性、反链、图谱、诊断、导出失败说明等。
- 可访问性和工程可维护性还有欠账：部分菜单/文件树仍用 `div` 承载交互，局部 inline style 较多，浏览器开发态会被 Tauri API 卡住。

## A. 写作主链路

- [ ] **1. 命令面板更像“快速打开”，还不是“命令中心”**

【建议优先】【中成本】

现状：`CommandPalette` 只有 `files` 和 `search` 两种模式，能快速打开文件和全文搜索，但菜单里的导航、视图、导出、文档属性、反链、图谱、模板等命令没有统一进入这里。

影响：用户记不住功能入口时，`Cmd+P` 不能兜底；后续功能越多，顶部菜单和状态栏会继续变拥挤。

  - [ ] 方案 A：保留现在的“快速打开”，另加一个“命令面板”。例如 `Cmd+P` 打开文件，`Cmd+Shift+P` 打开命令。
  - [x] 方案 B：合并成一个万能面板。输入框里同时搜“文件 / 标题 / 全文 / 命令”，用分组展示。
  - [ ] 方案 C：先做轻量版，只把“打开文档属性 / 查看反链 / 查看关系图谱 / 导出设置 / 切换视图 / 打开设置”接入现有面板。
  - [ ] 方案 D：把命令面板做成所有低频能力的默认入口，状态栏和标题栏只放高频按钮。

- [ ] **2. 分栏比例固定，用户不能按文档类型调整**

【建议优先】【中成本】

现状：分栏模式基本是编辑区和预览区各占一半，没有拖拽分隔线，也没有“编辑更宽 / 预览更宽”的预设。

影响：普通文章还可以，但遇到表格、代码、数据清单时，源码区半宽会频繁折行；遇到排版校对时，预览区又可能不够宽。

  - [ ] 方案 A：增加可拖拽分隔线，用户自己调比例，并记住每个窗口或全局比例。
  - [ ] 方案 B：增加三档布局按钮：编辑宽、均分、预览宽。
  - [ ] 方案 C：根据文档内容给建议，例如检测到大表格时提示“切到编辑宽”。
  - [ ] 方案 D：只在菜单里加“分栏布局”子菜单，不增加界面按钮。

- [ ] **3. Markdown 表格和数据文档在源码区不够好读**

【建议优先】【中成本】

现状：截图里的销售分析文档包含大量表格和数字，源码区在妙言式正文排版下很舒服，但表格列对齐、数字扫描和长行阅读不够稳定。

影响：Prism 既然支持导出和数据分析类 Markdown，就需要让表格编辑不痛苦，否则用户会切回 Typora、VS Code 或表格工具。

  - [x] 方案 A：给 Markdown 表格行启用更明显的等宽字体和更稳定的 tabular number。
  - [x] 方案 B：检测当前光标在表格里时，局部关闭换行，保留横向滚动。
  - [x] 方案 C：提供“表格友好模式”，编辑区更宽、等宽字体、行高更紧凑。
  - [x] 方案 D：做轻量表格编辑器，例如插入/删除行列、对齐列、格式化表格，但源码仍保持 Markdown。

- [ ] **4. 查找/替换底层支持选项，界面没有暴露**

【建议优先】【低成本】

现状：`SearchPanel` 的参数里有大小写、正则、全词，但现在固定为 `false`，界面上没有按钮。

影响：写长文、改术语、替换变量名时，用户会觉得搜索能力太弱；而且底层已经留了口子，不做会浪费已有设计。

  - [ ] 方案 A：在搜索框右侧加三个小按钮：大小写、全词、正则。
  - [ ] 方案 B：默认仍简洁，只在展开替换模式后显示高级搜索选项。
  - [x] 方案 C：把搜索选项放到一个小菜单里，避免搜索条变宽。
  - [ ] 方案 D：替换全部前增加确认提示，显示“将替换 n 处”。

- [ ] **5. 斜杠菜单内容越来越多，需要重新分组**

【建议优先】【中成本】

现状：斜杠菜单包含标题、表格、Mermaid、KaTeX、Callout、Toggle、代码块、图片、链接、导出设置和多种模板。能力很丰富，但现在是平铺列表。

影响：`/` 本来应该是“快速插入”，当列表变长以后，用户会依赖搜索记忆；新用户也不容易理解哪些是基础 Markdown，哪些是增强块，哪些是模板。

  - [x] 方案 A：按“基础 Markdown / 增强块 / 模板 / 导出设置”分组。
  - [ ] 方案 B：常用项置顶，模板折叠成二级选择。
  - [ ] 方案 C：输入 `/template` 后再进入模板搜索，不把所有模板平铺在第一层。
  - [ ] 方案 D：空行输入 `/` 时展示完整菜单，非空行只展示常用插入项，减少误触。

- [ ] **6. 大纲已经可用，但缺少“我现在在哪”**

【体验增强】【中成本】

现状：`OutlinePanel` 支持标题列表、搜索、点击跳转，但没有跟随正文滚动高亮当前标题。

影响：长文写作时，大纲不仅是跳转工具，也是定位工具。没有当前位置，高频滚动校对时价值会下降。

  - [ ] 方案 A：正文滚动时高亮当前所在标题。
  - [ ] 方案 B：点击大纲后正文跳转，同时给目标标题一个短暂高亮。
  - [ ] 方案 C：大纲顶部显示当前章节名。
  - [ ] 方案 D：支持折叠 H2/H3 分组，让长文大纲更短。

- [ ] **7. 空文档/无文档状态太轻，不能承接新用户动作**

【体验增强】【低成本】

现状：没有当前文档时，`DocumentView` 只显示一行空提示。

影响：首次启动、关闭文档、工作区为空时，用户不知道下一步该新建、打开文件、打开文件夹还是恢复最近文档。

  - [x] 方案 A：空状态给三个动作：新建文稿、打开文件、打开文件夹。
  - [ ] 方案 B：同时展示最近打开的 3-5 个文档。
  - [ ] 方案 C：如果有恢复快照，空状态优先提示恢复。
  - [ ] 方案 D：保持极简，只在空提示下方加快捷键提示。

- [ ] **8. 写作模式、预览模式、分栏模式的差异还可以说得更清楚**

【体验增强】【低成本】

现状：右上角有三个图标切换编辑/分栏/预览，图标本身克制，但只靠 tooltip 解释。

影响：熟手没问题，新用户需要试错；尤其“源码编辑”和“预览阅读”的心智可以更明确。

  - [ ] 方案 A：切换按钮改成 segmented control，图标保留，当前模式更明显。
  - [ ] 方案 B：首次使用时短暂显示文字标签，之后恢复纯图标。
  - [ ] 方案 C：设置里提供“纯图标 / 图标+文字”两种标题栏模式。
  - [ ] 方案 D：只优化 tooltip 文案和快捷键展示，不改布局。

## B. 入口与信息架构

- [ ] **9. 顶部菜单、右上图标、状态栏和命令面板职责有重叠**

【建议优先】【中成本】

现状：顶部菜单承载完整功能；右上角承载视图切换；状态栏承载统计、导出、专注、图谱、侧栏控制；命令面板承载文件和搜索。

影响：功能多起来以后，用户会问“这个功能到底在哪”。入口没有分层，后续每加功能都容易把状态栏或菜单塞满。

  - [x] 方案 A：定义入口分工：标题栏只放视图，状态栏只放状态和高频动作，命令面板收纳低频命令，菜单做完整兜底。
  - [ ] 方案 B：把“导航类”统一进命令面板和导航菜单，状态栏不再放图谱这类入口。
  - [x] 方案 C：把“写作插入类”统一给斜杠菜单和插入菜单，其他位置不重复。
  - [x] 方案 D：先写一份入口规则文档，后续每个新功能按规则放入口。

- [ ] **10. 状态栏已经克制，但仍有变成“功能收纳区”的风险**

【建议优先】【低成本】

现状：状态栏当前有字数/行列、ERROR、后台导出、关系图谱、专注、导出、侧栏和文件树模式相关入口。`CONTEXT.md` 已明确状态栏不应成为功能入口收纳区。

影响：状态栏越放越多，会破坏妙言式低噪声写作区，也会让真正的状态信息不突出。

  - [ ] 方案 A：状态栏只保留统计、ERROR、后台导出、专注、导出。
  - [x] 方案 B：关系图谱只在当前文档存在链接关系时显示。
  - [ ] 方案 C：把关系图谱、反链、文档属性全部移到命令面板和“导航”菜单。
  - [ ] 方案 D：提供状态栏自定义，用户可隐藏关系图谱、导出、专注等按钮。

- [ ] **11. macOS 下窗口内菜单与系统菜单容易显得重复**

【体验增强】【中成本】

现状：Prism 在窗口内绘制了一套菜单栏，macOS 系统顶部也会有应用菜单。截图里的窗口内菜单视觉清楚，但在 macOS 心智里容易和系统菜单重复。

影响：原生桌面感会被削弱；跨平台一致性和 macOS 原生感之间需要取舍。

  - [ ] 方案 A：macOS 只保留系统菜单，窗口内菜单隐藏。
  - [ ] 方案 B：macOS 保留窗口内菜单，系统菜单做最小化兜底。
  - [ ] 方案 C：窗口内菜单改成更轻的工具栏，只放插入、格式、导出等写作高频动作。
  - [ ] 方案 D：暂时不改，先观察真实使用中用户是否依赖窗口内菜单。

- [ ] **12. 文件树信息密度不错，但排序、过滤和模式切换不够明显**

【体验增强】【中成本】

现状：文件树有文件预览、树/列表模式、右键菜单和重命名能力；但模式切换在状态栏图标里，排序/过滤入口不够显性。

影响：工作区文档多时，用户会更依赖文件树。入口隐蔽会让“我知道有文件，但找起来慢”。

  - [ ] 方案 A：文件树顶部增加小工具条：搜索、排序、树/列表切换。
  - [ ] 方案 B：保留状态栏切换，但在文件树空白处右键菜单里突出排序和显示模式。
  - [ ] 方案 C：列表模式下显示最近编辑、路径、摘要；树模式下保持紧凑。
  - [ ] 方案 D：文件项摘要支持“紧凑 / 详细”切换。

- [ ] **13. 文件树和大纲像两个 tab，但二者的关系还可以更强**

【体验增强】【中成本】

现状：侧栏有“文件 / 大纲”两个页签。文件负责工作区导航，大纲负责当前文档导航。

影响：这个方向合理，但切换成本存在。写长文时，用户可能频繁在文件和大纲之间来回切。

  - [ ] 方案 A：保留 tab，但记住每个文档上次使用的是文件还是大纲。
  - [ ] 方案 B：在文件树顶部显示当前文档的小型大纲入口。
  - [ ] 方案 C：在大纲页顶部显示当前文件名和所在文件夹，避免用户迷路。
  - [ ] 方案 D：不合并，保持当前结构，只优化大纲当前标题高亮。

- [ ] **14. 文档属性、链接、反链、图谱都存在，但像散落的功能点**

【建议优先】【中成本】

现状：`DocumentPanelsController` 已经有属性、链接、反链、关系图谱、诊断等面板。能力方向对，但入口和展示形态还没有形成一个统一的“文档信息”体验。

影响：这些功能如果都各自用弹窗，会显得零散；如果都放状态栏，又会太重。

  - [x] 方案 A：建立“文档信息”轻面板，里面分属性、链接、反链、诊断几个 tab。
  - [ ] 方案 B：保持各自独立弹窗，但都从命令面板和导航菜单进入。
  - [ ] 方案 C：只把“属性 + 导出设置”合并，链接/反链/图谱保持独立。
  - [ ] 方案 D：暂缓合并，先把命令面板入口补齐。

- [ ] **15. 关系图谱入口现在偏重**

【暂缓观察】【低成本】

现状：只要文档有保存路径，状态栏就可能显示关系图谱按钮。但 Prism 的定位不是重型知识库，图谱应该是轻量辅助。

影响：如果图谱入口长期常驻，会暗示 Prism 是 Obsidian 式知识图谱产品，和单文档写作器定位有一点冲突。

  - [x] 方案 A：有链接或反链时才显示图谱入口。
  - [ ] 方案 B：默认从状态栏移除，只放命令面板和导航菜单。
  - [ ] 方案 C：保留状态栏入口，但允许用户在设置里隐藏。
  - [ ] 方案 D：暂时不改，等反链/图谱真实使用频率出来再决定。

- [x] **16. 设置中心已经清楚，但缺少搜索和“恢复推荐值”**

【体验增强】【中成本】

现状：设置中心有通用、写作、外观、导出、引用、文件几个分组，视觉上比较稳。但设置项多了以后，用户需要逐个 tab 找。

影响：设置中心会随着导出、主题、引用、文件安全继续变复杂。没有搜索和恢复默认，排错成本会高。

  - [x] 方案 A：设置顶部增加搜索框，按设置名和说明过滤。
  - [x] 方案 B：每个分组增加“恢复本页默认值”。
  - [x] 方案 C：复杂项增加“推荐值”按钮，例如导出质量、字体、引用。
  - [x] 方案 D：外观和导出设置增加预览，不让用户盲选。

## C. 导出、诊断与文档安全

- [x] **17. 导出前检查已经有雏形，但可以更像“看得懂的检查清单”**

【建议优先】【中成本】

现状：导出保存弹窗里有目标、质量、风险。方向对，但用户看到“风险”时，可能还不知道具体会影响什么。

影响：导出是 Prism 的重点能力。导出前越清楚，导出失败和结果不符合预期时的挫败感越低。

  - [x] 方案 A：导出前显示三项检查：图片、链接、渲染块，并标注通过/需注意。
  - [x] 方案 B：有问题时展示前 3 条具体问题，点击可定位。
  - [x] 方案 C：低风险时保持简洁，只显示“未发现阻断问题”。
  - [x] 方案 D：导出前检查和底部 ERROR 使用同一套诊断数据，避免两套说法。

- [x] **18. 导出失败详情偏技术，普通用户需要更可读的原因**

【建议优先】【中成本】

现状：导出失败弹窗提供摘要、恢复建议和原始 diagnostic textarea，可以复制诊断。这对排查很好，但普通用户更需要直接原因。

影响：如果用户只看到一大段技术诊断，会不知道是图片丢了、权限问题、Pandoc 问题，还是渲染失败。

  - [x] 方案 A：失败弹窗顶部给“可能原因列表”，原始诊断折叠在下方。
  - [x] 方案 B：按导出阶段展示：准备、渲染、资源、写文件、外部工具。
  - [x] 方案 C：给每类失败一个下一步动作，例如“更换保存位置”“检查图片路径”“安装 Pandoc”。
  - [x] 方案 D：保留复制诊断按钮，但按钮文案更明确，例如“复制给开发者排查”。

- [ ] **19. 保存状态的脏标记太轻，失败状态需要更明显**

【建议优先】【低成本】

现状：标题栏文件名旁有一个脏状态小圆点，符合低噪声原则。但保存失败、冲突、只读等状态需要更高优先级表达。

影响：写作器最重要的是不丢稿。保存失败如果不够明显，会直接影响信任。

  - [ ] 方案 A：未保存只用小圆点，保存失败时改成更明确的文字或警告图标。
  - [x] 方案 B：保存失败出现非打扰 toast，同时标题栏保留失败状态。
  - [ ] 方案 C：点击文件名区域打开保存状态详情：路径、错误、可执行动作。
  - [ ] 方案 D：冲突状态提供“重新载入 / 另存为副本 / 查看本地内容”三个动作。

- [ ] **20. 恢复快照能力需要更容易被用户理解**

【体验增强】【中成本】

现状：项目里已有恢复相关逻辑和测试，但从 UX 上看，普通用户不一定知道什么时候会生成快照、去哪恢复。

影响：恢复能力只有在用户紧张时才会用；那时候入口必须非常明确。

  - [x] 方案 A：异常启动时自动弹恢复提示。
  - [x] 方案 B：文件菜单增加“查看恢复快照”，只在有快照时可用。
  - [x] 方案 C：保存失败时直接给“保存副本 / 打开恢复目录”。
  - [x] 方案 D：设置里增加恢复快照说明和清理入口。

- [ ] **21. ERROR 面板方向正确，但诊断应进一步按用户动作组织**

【体验增强】【中成本】

现状：诊断面板按类型展示链接、图片、渲染、表格、排版等问题，点击可定位。

影响：如果诊断只列问题，用户还要自己判断怎么修。更好的体验是“问题 + 为什么重要 + 怎么处理”。

  - [ ] 方案 A：每条诊断都固定展示“建议动作”。
  - [ ] 方案 B：支持一键过滤：只看阻断导出的问题。
  - [ ] 方案 C：按严重程度分组：必须处理 / 建议处理 / 可忽略。
  - [ ] 方案 D：允许用户忽略某类排版建议，避免 ERROR 变吵。

## D. 可访问性、键盘与开发验证

- [ ] **22. 菜单栏和文件树部分交互元素语义不够完整**

【风险修复】【中成本】

现状：窗口内菜单根项和文件树行有不少 `div + onClick`。视觉上能用，但语义、键盘导航和屏幕阅读器支持不够标准。

影响：这类问题短期不影响鼠标用户，但会影响键盘流、无障碍和自动化测试，也会让复杂交互后续更难维护。

  - [ ] 方案 A：菜单根项改成 button，并补齐 `aria-haspopup`、`aria-expanded`。
  - [ ] 方案 B：文件树改成 tree/treeitem 语义，支持方向键、Enter、F2、Esc。
  - [ ] 方案 C：命令面板列表补 `role=listbox/option` 和 `aria-selected`。
  - [ ] 方案 D：先只补键盘操作，不大改 DOM 结构。

- [ ] **23. 浏览器开发态会被 Tauri API 绊住**

【风险修复】【低成本】

现状：`TitleBar` 初始化时直接调用 `getCurrentWindow()`。在纯浏览器/Vite 环境下，这类 Tauri API 容易导致白屏，影响截图、Story、组件调试。

影响：这不是普通用户问题，但会影响 UX 验证效率。设计和交互要经常截图，如果浏览器态打不开，迭代会慢。

  - [ ] 方案 A：做 Tauri window adapter，非 Tauri 环境返回 no-op window。
  - [ ] 方案 B：只在点击最小化/最大化/关闭时懒调用 Tauri API。
  - [ ] 方案 C：给组件预览单独建 story/demo route，不加载 Tauri-only shell。
  - [ ] 方案 D：保留当前实现，但把 UX 截图固定走 Tauri 真机流程。

- [ ] **24. 内联样式和局部 `<style>` 会增加长期视觉漂移风险**

【风险修复】【中成本】

现状：文件树、大纲、文档空状态、分栏容器等地方仍有不少 inline style 和组件内 `<style>`。设置中心也有较多局部 style 对象。

影响：现在看起来没问题，但后续换主题、改密度、做深色或截图基准时，样式会分散难查。

  - [ ] 方案 A：每次改某个区域时，顺手把该区域 inline style 收敛到 CSS module。
  - [ ] 方案 B：先集中处理文件树和大纲，因为它们是侧栏核心体验。
  - [ ] 方案 C：建立一组 Miaoyan UI primitives：按钮、输入框、列表项、弹窗、segmented control。
  - [ ] 方案 D：不做一次性大重构，只禁止新增复杂 inline style。

- [ ] **25. 截图基准缺少固定流程**

【风险修复】【中成本】

现状：这次已经有当前截图资产，但还不是稳定的截图基准测试流程。

影响：Prism 的 UX 很依赖“看起来有没有变味”。如果没有固定截图，后续小改动容易破坏妙言风格却没人发现。

  - [ ] 方案 A：建立 5 张固定截图基准：编辑、分栏、预览、命令面板、设置。
  - [ ] 方案 B：每次 UI 改动跑 Playwright/Tauri 截图，人工比对。
  - [ ] 方案 C：只在 release 前跑截图基准，平时不增加负担。
  - [ ] 方案 D：把截图基准和 UX 报告模板绑定，每次评审自动更新。

- [ ] **26. 快捷键体系有菜单，但用户不一定记得住**

【体验增强】【低成本】

现状：菜单里有快捷键，帮助菜单也有快捷键入口。但高频动作散在不同位置，用户不一定会主动打开帮助。

影响：Markdown 写作器的效率很依赖键盘。快捷键不可发现，会让熟手效率上不去。

  - [ ] 方案 A：命令面板结果右侧显示快捷键。
  - [ ] 方案 B：首次使用搜索、分栏、导出、斜杠菜单时给轻提示。
  - [ ] 方案 C：帮助菜单里的快捷键面板支持搜索。
  - [ ] 方案 D：状态栏 hover 统计区域时提示常用快捷键入口。

## E. 视觉一致性与长期产品感

- [ ] **27. 妙言风格已经成立，但主题/字体设置需要避免“换色后变味”**

【体验增强】【中成本】

现状：Prism 已经以妙言风格为默认，并支持内容主题、字体来源、导出主题等设置。

影响：主题能力是优势，但如果每个主题只换颜色、不管编辑区、预览、导出、代码块和状态栏的一致性，整体会变散。

  - [ ] 方案 A：主题预览卡展示编辑、标题、代码块、引用、表格五种元素。
  - [ ] 方案 B：编辑字体、预览字体、导出字体默认跟随主题，但允许高级用户分开设置。
  - [ ] 方案 C：每个主题必须通过截图基准，保证不破坏核心布局。
  - [ ] 方案 D：先不扩展主题数量，优先打磨默认妙言主题。

- [ ] **28. 设置、弹窗、面板的层级可以更统一**

【体验增强】【中成本】

现状：设置中心是大 modal，反链/属性/导出失败也是 modal，诊断是 popover 风格。各自能用，但层级规则还可以更明确。

影响：当功能变多后，用户会感觉“又弹了一个东西”，不清楚哪些是临时提示，哪些是工作面板。

  - [ ] 方案 A：定义三种层级：toast 只通知，popover 处理轻任务，modal 处理必须完成/取消的任务。
  - [ ] 方案 B：反链、链接、属性改成轻面板，不用大 modal。
  - [ ] 方案 C：导出保存、设置中心、恢复快照保留 modal。
  - [ ] 方案 D：先写层级规则，不急着改所有现有弹窗。

- [ ] **29. 文案风格整体克制，但有些地方还偏“系统设置说明”**

【体验增强】【低成本】

现状：设置、导出、诊断里的说明多数清楚，但有些文案更像工程解释，不像写作器给用户的提示。

影响：Prism 的产品感来自“安静但可靠”。文案如果过技术，会削弱这个气质。

  - [ ] 方案 A：统一文案原则：短句、少术语、先告诉用户影响。
  - [ ] 方案 B：诊断类文案改成“发生了什么 / 为什么影响 / 怎么处理”。
  - [ ] 方案 C：设置项 hint 控制在一行内，复杂解释放 tooltip。
  - [ ] 方案 D：只处理导出失败、保存失败、恢复快照这些高压场景文案。

- [ ] **30. 低频高级能力需要降噪，不要抢写作主流程**

【建议优先】【低成本】

现状：反链、图谱、文档属性、导出设置、排版诊断都很有价值，但它们不是每次写作都需要。

影响：Prism 最核心的竞争力是“打开就写”。高级能力如果太显眼，会把产品心智带向复杂工作台。

  - [ ] 方案 A：高级能力默认放命令面板，只有有上下文时才浮现。
  - [ ] 方案 B：设置里提供“简洁写作模式”，隐藏图谱、属性、诊断以外的低频入口。
  - [ ] 方案 C：按文档类型浮现能力，例如检测到链接多时提示反链，检测到导出字段时提示属性。
  - [ ] 方案 D：保留所有入口，但统一降低视觉权重。
